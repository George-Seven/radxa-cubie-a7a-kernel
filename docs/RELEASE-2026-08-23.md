# Debian 13 for the Radxa Cubie A7A

Building a custom kernel and DTB for the Radxa A7A to work on Debian 13 has been a
long and rewarding journey that I'm very proud of, and it's the first real
accomplishment I've published on GitHub.

A year ago I bought this board, looked at the specs, and thought: this has serious
hardware for the price. I bought it immediately. Radxa's site had tons of
documentation, but they had only shipped Debian 11. I downloaded it and yes, it
worked — but there was a lot of mismatch between how the software and the hardware
talked to each other.

I did some researching and found that I needed to edit the DTB so the hardware and
software would actually communicate properly. And that I could update the kernel
while I was at it. I spent tireless nights editing the DTB, putting it into the
board, getting it wrong, pulling it back out to edit again — over and over. There
were a few times I was nearly done and the image got overwritten or corrupted, and
I lost months of work.

I'm proud to announce that Debian 13 for the Radxa A7A is here, and it's more
stable than ever. It has a built-in clocks app and a small LLM app. It outperforms
the Pi 5 by a mile, and it's genuinely impressive for everyday tasks and games.

I hope you enjoy it. If there are any issues, please let me know.

## ⚠️ Read this before you flash anything

**Use at your own risk.** This is community work, not an official Radxa release.
It runs the SoC well beyond its datasheet specification — the A76 cores at 3.0 GHz
against a 2.0 GHz spec, and the memory at 2040 or 2136 MHz against an 1800 MHz
stock. It has been tested on my board. Silicon varies between units, and something
that runs for weeks on mine may not be stable on yours.

**You must have a cooler on your board.** Not optional. Without active cooling the
A76 cores will hit the 80 °C throttle point under sustained load and stay there,
and the maximum-overclock profile raises idle power on top of that. My board runs a
PWM fan, and the numbers below are measured with it fitted.

If a board misbehaves — random segfaults, filesystem corruption, or boots that hang
before a console appears — **remove the overclock profile first**, before debugging
anything else:

```sh
sudo apt remove a7a-oc-profile
```

Instability from memory overclocks is not always immediate. It can take hours of
load, or a warm room, to show up. Don't run the maximum variant on a board holding
data you care about until you've soaked it yourself.

## Cooling and temperatures

Measured on my board so you have something to compare against. Configuration:
CPU governor `performance` (A76 3.0 GHz / A55 2.8 GHz), DSU 1352 MHz, DRAM 2040 MHz,
PWM fan fitted, room temperature roughly 21 °C.

**Thermal trip points on this SoC:**

| trip | temperature | what happens |
|---|---|---|
| active | **50 °C** | fan ramps |
| passive | **80 °C** | CPU throttles |
| critical | **110 °C** | shutdown |

**Idle, desktop running:**

| sensor | temperature |
|---|---|
| A76 cluster | 33–37 °C |
| A55 cluster | 34–35 °C |
| DRAM | 33–35 °C |
| GPU | 33–37 °C |
| NPU | 33–34 °C |
| board skin | 30–31 °C |

**Under sustained all-core load** (`stress-ng --cpu 8`, 90 seconds):

| elapsed | A76 | A55 | DRAM | GPU | skin |
|---|---|---|---|---|---|
| 10 s | 61 °C | 60 °C | 47 °C | 51 °C | 36 °C |
| 30 s | 64 °C | 60 °C | 53 °C | 60 °C | 36 °C |
| 60 s | 70 °C | 68 °C | 54 °C | 60 °C | 37 °C |
| **80 s (peak)** | **71 °C** | 69 °C | 62 °C | 64 °C | 37 °C |
| +30 s after load | 42 °C | 43 °C | 43 °C | 43 °C | 32 °C |

So under a worst-case CPU load it settles around **70–71 °C**, roughly 9 °C below
the throttle point, and drops back to the low 40s within thirty seconds of the load
ending.

**How to compare your board:** run `a7a-clock status`, or

```sh
for z in /sys/class/thermal/thermal_zone*; do
  echo "$(cat $z/type): $(( $(cat $z/temp) / 1000 ))C"
done
```

If your idle temperatures are much above the mid-30s, or you cross 80 °C under
load, you need better cooling before running the maximum variant. A soak under
`stress-ng` at 1352 MHz DSU has been measured as high as **88.6 °C** — above the
passive trip — so headroom is real but not unlimited.

## What's in the release

Two variants, sharing one kernel:

**Standard** — kernel, device trees, headers, board config, desktop config, and the
LLM app.

**Maximum overclock** — the above plus the clock control app and a persistent
overclock profile.

Everything installs as real Debian packages, so `dpkg` knows about them, DKMS works,
and updates don't quietly break your boot menu.

## The journey, in numbers

Most of what follows was found the slow way: change one thing, reboot, measure,
write it down. A lot of it contradicts the obvious guess.

### RAM — the wall was voltage, not timings

Allwinner shipped this SoC at **1800 MHz** (3600 MT/s). Radxa's stock image ran the
same. The 8/12GB parameter release later moved it to **2040**.

Getting past 2040 took roughly **350 automated cold-boot training samples** on a
purpose-built FEL rig, because the failure mode only shows up on a *cold* boot — a
warm retrain lies and passes even at speeds that never boot.

Every timing knob turned out to be a dead end. Vref, drive strength, ODT, per-lane
trims: all flat or harmful. The thing that actually moved the wall was the **VDD2
DRAM core rail**.

| clock | data rate | VDD2 1080 (stock) | VDD2 1120 (JEDEC max) |
|---|---|---|---|
| 2040 | 4080 MT/s | 8/8 — daily driver | — |
| 2088 | 4176 MT/s | 2/2 | — |
| 2112 | 4224 MT/s | 4/10 — coin flip | 8/8 |
| **2136** | **4272 MT/s** | 0/8 — never | **9/9 — ships as maximum** |
| 2400 | 4800 MT/s | 0/8 | 0/8 — the real ceiling |

At stock voltage 2136 **never** trained. At 1120 mV — still inside the JEDEC VDD2H
maximum, not an overdrive — it trained 9 times out of 9. That one rail was the whole
wall.

Bandwidth went from **14.4 GB/s** theoretical at 1800 to a measured **16.4 GB/s**
stream peak at 2040, and higher again at 2136.

2400 MT/s is where the SoC genuinely stops. It's the datasheet ceiling and it failed
every single attempt regardless of voltage.

### CPU — 3.0 GHz is the clock driver, not the silicon

The A76 cores run at **3.0 GHz** and the A55 cores at **2.8 GHz**. Allwinner's
datasheet specifies **2.0 GHz** for the A76 cluster, so what ships here is already
**+50% over spec**.

I tried for 3.2 GHz. Added the OPP to the device tree, and cpufreq accepted it
completely — `scaling_max_freq` read 3200000, the governor reported it as active.
The hardware simply didn't deliver:

| | single-core sysbench |
|---|---|
| 3.0 GHz (stock OC) | 943 ev/s |
| "3.2 GHz" | 947 ev/s |
| what 3.2 should give | ~1006 ev/s |

Zero scaling. All-core performance actually *regressed*, from 4550 to 4025. Temps
sat at 44 °C throughout, so it wasn't thermal, and the voltage rail moved cleanly to
1200 mV, so it wasn't power.

The limit is the **sunxi-ng CCU clock driver**, which clamps the A76 cluster PLL at
3.0 GHz. An OPP table entry is necessary but not sufficient — the clock driver
mis-programs anything above its PLL maximum. Going higher is a kernel driver
project, not a DTB edit, and it may well be capped for a real silicon reason at an
already-stretched +50%.

### DSU / L3 — the multiplier nobody mentions

The DSU (the interconnect and L3 between the cores and memory) runs at **780 MHz**
by default. The vendor's own OPP table goes to **1352 MHz**, and unlike the CPU PLL,
it takes the full rate at runtime with no clamp.

Memory bandwidth, same boot, RAM at 2136:

| DSU | memory | temp |
|---|---|---|
| 780 MHz (stock) | 29,578 MiB/s | 61.6 °C |
| 988 MHz | 35,957 MiB/s | 62.6 °C |
| **1352 MHz** | **37,677 MiB/s** | 63.2 °C |

Here's the part worth knowing, because it's easy to draw the wrong conclusion. The
DSU raise is only worth anything **in combination with the RAM overclock**:

| | DSU 780 | DSU 1352 | gain |
|---|---|---|---|
| RAM 854 | 21,385 MiB/s | 21,586 MiB/s | **+0.9% — nothing** |
| RAM 2136 | 28,374 MiB/s | 37,295–39,030 MiB/s | **+31–38%** |

At slow RAM the DSU does nothing, because DRAM is the bottleneck. At fast RAM the
780 MHz DSU *becomes* the bottleneck and throttles the bandwidth the RAM overclock
paid for. **The two overclocks compound; neither delivers its full value alone.**

One warning: don't measure this with a CPU benchmark. sysbench's CPU test is
L1/L2-resident and completely DSU-insensitive — it reads 4532 vs 4542 across the
entire ladder. It'll tell you the DSU raise did nothing.

Under a 12-minute stress-ng soak at 1352 the board peaked at **88.6 °C**, above the
80 °C passive trip. Keep it ventilated.

### GPU — it works, but only outside X

The PowerVR B-Series BXM-4-64 works. Getting to it is the trick.

**Hardware OpenGL ES is reachable only outside X.** The Xorg modesetting driver
offers DRI3 only when glamor is enabled, and glamor can't be used on this display
engine (see below) — so under X, EGL silently falls back to software rendering.

```
GBM platform          → PowerVR B-Series BXM-4-64    hardware
Surfaceless platform  → PowerVR B-Series BXM-4-64    hardware
X11 platform          → softpipe                      software
```

The way through is `SDL_VIDEODRIVER=kmsdrm`, which bypasses X entirely. SuperTuxKart
then reports:

```
OpenGL vendor:   Imagination Technologies
OpenGL renderer: PowerVR B-Series BXM-4-64
OpenGL ES 3.2 build 24.2@6603887
```

That's Imagination's proprietary driver on the real chip. The same game under X on
software rendering managed about **10 fps**; on the GPU it's smooth, at 34% of one
CPU core. Vulkan works everywhere, including under X.

GPU clock ships at **1008 MHz**, with 600/800/1200 MHz device tree variants
available.

### NPU

The NPU runs at 492 / 852 / 1008 MHz and has its own devfreq node. ResNet50 inference
measures **7.49 ms** on the vendor sample.

### The cursor trail bug — a one-line kernel fix

This one deserves its own section, because it shaped everything about how the
desktop is configured.

Every A7A image to date had a mouse cursor that smeared and left trails that never
cleared. The vendor's answer was a compositor (`picom --no-use-damage`) that
repainted the entire screen every frame, driven by a helper daemon that manufactured
30 Hz of fake damage purely to keep it repainting. That cost about **60% of a CPU
core** on a 1024×600 panel.

The actual cause: the vendor DRM driver never implemented the `.dirty` callback, so
the `DIRTYFB` ioctl returned `-ENOSYS`. The X server probes with exactly that ioctl
and, on failure, **permanently disables damage tracking** — logging a line that
appears in every A7A Xorg log ever posted:

```
(II) modeset(0): Disabling kernel dirty updates, not required.
```

That message isn't X deciding the feature is unnecessary. It's X being told the
kernel can't do it. With damage tracking off, dirtied regions never reach the panel,
so anything drawn once stays there forever.

The fix is one line, using the same helper rockchip, vmwgfx and amdgpu use:

```c
.dirty = drm_atomic_helper_dirtyfb,
```

## Before and after

| | before | after |
|---|---|---|
| Xorg idle CPU | ~60% of a core | **~2%** |
| compositor | picom, always running | **removed** |
| damage helper daemon | 30 Hz, always running | **removed** |
| cursor trails | hidden by full repaints | **fixed at the source** |
| DSU / L3 | 780 MHz every boot | **1352 MHz, persistent** |
| CPU governor | schedutil, idling at 1612 MHz | **performance, 3000 MHz** |
| RAM | 1800 MHz stock | **2040 standard / 2136 maximum** |
| gigabit ethernet | corrupted transmits | **fixed** |
| GPU in games | ~10 fps, software | **hardware, smooth** |

The desktop is also *more responsive* than it was on the GPU path — not a
compromise. The old configuration was repainting 614,400 pixels thirty times a
second just to force a flush.

## Honest limits

Some things are not solved, and it's better to say so:

- **The desktop renders in software.** That's deliberate. Glamor works on this GPU
  but its output doesn't reliably reach the scanout buffer, so the choice was a
  60%-CPU compositor or software 2D at 2%. On a screen this size there's very little
  2D work to accelerate, and it measures faster.
- **Windowed OpenGL apps get software rendering**, for the same reason. Fullscreen
  games via KMSDRM, and anything using Vulkan, get the real GPU.
- **No hardware cursor plane exists** on this display engine, so KMS fullscreen games
  show no mouse pointer. Keyboard navigation works. A proper fix means adding a
  cursor plane to the DRM driver.
- **3.2 GHz is blocked by the clock driver**, not by heat or voltage.
- **2400 MT/s RAM is a genuine hardware ceiling.** It never trained, at any voltage.
- **The maximum overclock was validated on one board.** Silicon varies. If a board
  acts up — random segfaults, filesystem corruption, boots that hang before a console
  — remove the overclock profile first, before debugging anything else.
